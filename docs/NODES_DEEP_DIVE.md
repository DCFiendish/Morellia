# Aechronis `nodes` — Deep Technical Reference & Bug Audit

Companion to [RESEARCH.md](RESEARCH.md), split out because this is a much deeper, code-level document: the goal is to understand `nodes` mechanically well enough to catch bugs before they hit production at 200+ concurrent players, not to plan features. Built from (1) the original `phonon/minecraft-nodes` documentation at nodes.soy — the design `nodes` is ported from — and (2) three independent, exhaustive read-throughs of the actual `Aechronis/nodes` source (master branch), each explicitly tasked with hunting for bugs, races, and edge cases rather than just describing behavior.

Every finding below is cited to a real file/class/function. Severity labels (CRITICAL/HIGH/MEDIUM/LOW) reflect likely production impact at 200+ concurrent players, not theoretical severity.

> **Re-verified 2026-07-30 against current `master` (HEAD `2952518`, "refactor: set respawnPoint to town spawn on death").** Despite a large intervening refactor (73 files changed, the ~2200-line `Nodes.kt` god-object split apart, `objects/Command.kt` deleted in favor of the shared `net.aechronis.utils.Command`, and new `Plot`/`Waypoint`/`WaypointMenu`/`WaypointDisplayManager`/`MinimapMarkerRenderer`/`MinimapIcons`/`NodesCommand` files added), **every CRITICAL/HIGH item and nearly every MEDIUM/LOW item is confirmed still present**, often relocated but mechanically identical. Notable exceptions and new findings:
> - **M15 partially fixed**: `Minimap.render()`'s async path now wraps its `CompletableFuture` in `.whenComplete { ..., throwable -> MinecraftServer.getExceptionManager().handleException(throwable) }` — exceptions there are now actually logged. `WarSerializer.save()`'s async write still has **zero** exception handling — the war-autosave half of this finding is unfixed.
> - **Part 4 divergences are now definitively resolved, not just "unconfirmed":** a full-repo grep for `power`/`claimCost`/`unclaimPenalty`/`resourceConstant` returns zero matches — **the original phonon power-point claiming economy is confirmed absent**, territory assignment is purely admin/FlagWar-driven. A full-repo grep for `peace`/`truce` also returns zero matches — **peace treaties/48-hour truce mechanics are confirmed absent**, not just unimplemented-and-unchecked. See [`research-todo/06-economy-and-progression.md`](research-todo/06-economy-and-progression.md), which cited these as open questions — they're closed now.
> - **New bugs found in the previously-unaudited Plot/Waypoint code**: `Plot.at` (`Plot.kt`) is an unsynchronized linear scan over `town.plots` called on *every* block interaction in a town — same concurrency-risk shape as H3, in code that didn't exist at the original audit. `MinimapMarkerRenderer.markerMetadata`/`MinimapIcons`' icon-lookup functions add two more hardcoded exhaustive `when(scale)` blocks with the same 4/12-only trap as the original LOW item. Full detail in the git history / available on request — not reproduced in full here to avoid re-duplicating the MEDIUM/LOW catalog below, which remains otherwise accurate as-is.
> - A latent risk worth flagging for whoever eventually fixes C2 (war-state-loss on restart): `FlagWar.loadAttack()` calls `createAttack()`, which unconditionally re-places the flag block and regenerates the sky beacon — a naive fix that just calls `loadAttack` per saved attack on startup would double-place/regenerate structures rather than reattaching to what's already physically there from before the restart. Design the fix around this, don't just wire up the existing dead code path as-is.

## Part 1 — Original design (`phonon/minecraft-nodes`, via nodes.soy)

This is the design `nodes` was ported from. Not all of it necessarily carried over — see Part 4 for confirmed divergences.

**Territories & claiming**: map is pre-segmented into chunk-grid territories, each with fixed resources. Towns claim territories via a **power-point economy**: base power 30, +5 per player, +up to 20/player accumulating at 1/hour (rewards sustained engagement, discourages alt-account spam). Claim cost formula: `cost = base + rc + rs × a × chunks`, where `rc`/`rs` (resource constant/scale) vary by territory resources — rare resources (diamonds) cost far more than common ones (wheat). Unclaiming imposes a decaying power penalty equal to the territory's cost; exceeding a town's power budget imposes a 50% resource penalty across all its territories.

**Diplomacy & war**: admin-controlled war mode, declared via `/war`. FlagWar is the capture mechanic: place a fence-block "flag" (must see sky, can't be underground/underwater) from a territory edge/captured chunk/ally territory; undefended flags auto-capture their chunk after a timer; capturing the **home chunk** captures the whole territory. Captured territory becomes **occupied** (occupier taxes income/ore/crops/breeding, cannot build/access chests) until **annexed** (folded into the town permanently, no more power cost, full rights, no more tax). Peace treaties (`/peace`) create a 48-hour truce. Allied towns/nations cannot declare war on each other, but existing alliances don't auto-join a declared war.

**Town protections**: protects specific containers (chests/trapped chests/furnaces) via `/t protect`, not whole plots — **the original design explicitly has no per-chunk/per-territory/per-player permissions**, only five uniform town-wide groups (Trusted, Town, Nation, Ally, Outsider) across six permission types (Interact, Build, Destroy, Chests, Items [inactive], Income).

**Resource nodes**: four categories — Income (periodic scheduled yield), Ore (hidden drop-rate-on-mining-stone), Crops (growth speed), Animals (breeding success rate). Fractional yields (<1.0) are a random roll (`random() < amount` → 1 item); whole yields (≥1.0) give that integer amount; occupation taxes round fractional income up (`Math.ceil`). Ore yields support a simple `"item": rate` or advanced `"item": [rate, min, max]` format. Neighbor-territory effects (`neighbor_income`, `neighbor_ore`, etc.) let adjacent territories boost each other; same-property rates from multiple sources sum, multipliers apply by priority order.

## Part 2 — How Aechronis' Minestom port actually works

### 2.1 Core domain objects

- **`Coord`/`TerritoryId`** (`objects/Coord.kt`): plain chunk-coordinate key types, fine as map keys.
- **`TerritoryChunk`** (`objects/TerritoryChunk.kt`): holds a **direct mutable reference** to its owning `Territory`, plus `var attacker`/`var occupier`. The class's own doc comment admits this must be manually kept in sync whenever a `Territory` is swapped at runtime — there's no abstraction enforcing that (see bug catalog).
- **`Territory`** (`objects/Territory.kt`): a `data class` carrying two genuinely mutable fields, `var town: Town?` / `var occupier: Town?` (in-source TODO: "find way to get rid?"), written from many call sites with no synchronization. Also owns `TerritoryResources` (income/ore rate accumulation with neighbor-modifier propagation) and `attackerTimeMultiplier`/`defenderTimeMultiplier` (feed directly into FlagWar's attack-time formula — this is the confirmed hook point for the territory-tier system planned in RESEARCH.md §15).
- **`Town`** (`objects/Town.kt`): `leader: Resident?`, `officers: HashSet<Resident>`, `residents: HashSet<Resident>`, `spawnpoint: Pos`, `territories`/`annexed`/`captured: HashSet<TerritoryId>`, `home: TerritoryId`, `income: IncomeInventory`, `nation: Nation?`, `playersOnline`, `plots: LinkedHashMap<String, Plot>`, `protectedBlocks`, `applications` (pending join requests), `color`, `name`, `uuid`. **No tier/level field exists** (confirmed — the tier *design* lives only in `Aechronis/guides`, unimplemented; see RESEARCH.md §15).
- **`Nation`** (`objects/Nation.kt`): towns, capital, allies/enemies (nation-scoped, not town-scoped despite the deserializer parsing town-level allies/enemies too — see §2.2 dead-code finding).
- **`Resident`** (`objects/Resident.kt`): per-player state — town/nation membership, trusted flag, waypoints, ignored-players list.
- **`Plot`** (`objects/Plot.kt`): sub-territory claims with per-player and per-group ACLs (`PermissionsGroup.TOWN/NATION/ALLY/TRUSTED/OUTSIDER`), validated against the parent territory's current owner at creation/redefinition time only (not re-validated on ownership change — see bug catalog).
- **`IncomeInventory`** (`objects/IncomeInventory.kt`): the actual town treasury — a `Map<Material, Int>` presented as a chest GUI (`/town income`), the game's real material-based economy (§9/§11 of RESEARCH.md).
- **`OreSampler`/`OreDeposit`/`OreBlockCache`** (`objects/OreSampler.kt` etc.): the hidden-ore-on-mining-stone system RESEARCH.md §11 is built around. `OreSampler` builds a per-territory weighted item table (Vose's-alias-method) from `OreDeposit(material, dropChance, minAmount, maxAmount, ymin, ymax)` entries; `OreBlockCache` is the anti-exploit guard preventing "place block, mine it, repeat" farming (see bug catalog — this is one of the most serious findings in the whole audit).
- **`ResourceNode`** (`objects/ResourceNode.kt`): cleanly implemented as an immutable copy-on-write fold over attribute application — one of the better-engineered files in the domain layer, no findings.

### 2.2 Persistence

`nodes` uses **hand-rolled JSON**, no database: `Serializer.kt` builds JSON via manual `StringBuilder`/string-template concatenation (not a library like Gson's builder), `Deserializer.kt` reads it back via manual `JsonObject.get(...)?.as...` calls with per-field null-fallback logic. This is single-process by construction (confirmed earlier in RESEARCH.md §7a) — no locking, no versioning, nothing that would let two JVMs share this data safely.

A `SaveState` memoization pattern (`needsUpdate()` dirty flag + a lazily-built, supposedly-immutable snapshot per `Town`/`Nation`/`Resident`) avoids re-serializing unchanged entities on every autosave tick — reasonable design, but entirely dependent on every mutation path remembering to call `needsUpdate()` (unenforced by the compiler; a regression risk for any future change, not a currently-confirmed bug). `SaveManager`/`IncomeManager` (`tasks/`) schedule periodic saves (dirty-flag + fixed period, explicitly designed in-source to avoid disk-I/O spam from command mashing) and hourly income runs (wall-clock-hour-boundary triggered).

### 2.3 War/siege system (`war/`)

`FlagWar` is a singleton holding all live siege state (per-player attack lists, chunk→attacker maps, occupied-chunk set). `beginAttack()` validates flag placement (not-already-attacked, not-already-captured, enemy ownership, border/edge rules, sky visibility, per-player attack cap) and delegates to `createAttack()`, which computes attack duration from a global base multiplied by wilderness/home/attacker-vs-defender multipliers (the exact formula already confirmed in RESEARCH.md §15's tier-system hook). `Attack` is a self-scheduling repeating task with a packet-only text display and boss bar. `finishAttack()` handles capture/annex/liberate/defend outcomes. Alliances (`war/Alliance.kt`) are nation-level, request/accept gated, and you cannot ally an active enemy.

### 2.4 World-interaction listeners

- **`NodesWorldListener.kt`**: the permission-gating engine for block break/place/interact, already documented in RESEARCH.md §6 (plot ACL → town permission matrix → occupier override → war override) and §11 (hidden-ore sampling + anti-exploit cache).
- **`NodesPlayerDamageListener.kt`**: friendly-fire cancellation by nation/ally relationship, already documented in RESEARCH.md §6.
- **`NodesPlayerMoveListener.kt`**: chunk-cross territory announcements + home-teleport-warmup cancellation on movement, already documented in RESEARCH.md §12/§15.

### 2.5 Minimap system

Already documented in RESEARCH.md §15 — packet-only text-display entity, RGB-channel-encoded territory/waypoint data via a custom font, refreshed on chunk-boundary crossing and hash-gated to avoid redundant packets. `Resident.renderMinimaps()` is the global force-refresh hook, called from a wide range of war/diplomacy/territory mutation sites (see bug catalog — this fan-out is a real scaling concern).

### 2.6 Command surface

Already inventoried in RESEARCH.md §15 (11+ command groups). The argument layer (`commands/arguments/`) defends against JSON-breaking input via `ArgumentSanitizedString` (rejects `"`/`{`/`}`, escapes `$`/`%`) applied consistently everywhere a player names something persisted (towns, nations, plots, ports) — see bug catalog for the one confirmed gap in this defense.

## Part 3 — Confirmed bugs & design flaws, by severity

### CRITICAL

**C1. `/nodesadmin building create port <name>` ignores the typed name — only the first port ever created on the server can ever succeed.**
`NodesAdminBuildingCreateCommand` calls `Port.create(name, ...)` where `name` resolves (via variable shadowing) to the **command's own registered name string** (`"create"`), not `context[nameArg]` — the parsed argument is never read. Every port gets created with the literal name `"create"`; `Port.create()` rejects duplicate names, so after the first successful call, **every subsequent port-creation attempt fails** with a misleading "port already exists" error, regardless of what name was typed. Same command block also has a broken string-template bug in its confirmation message (`"$context[tierArg]"` prints the object's `toString()` instead of the value) — a second, unrelated defect in the same handler, suggesting it was never tested end-to-end.

**C2. War-attack persistence is broken end-to-end — every restart during an active siege permanently destroys it and litters the world with orphaned structures.**
`WarSerializer` faithfully writes in-progress attacks to `war.json` on every autosave. But `WarDeserializer.fromJson()` **never reads the `"attacks"` key at all**, and `FlagWar.loadAttack()` — the function clearly written to reconstruct an `Attack` from saved JSON — is **never called anywhere in the codebase** (confirmed via full-repo grep). `FlagWar.load()` unconditionally clears all attack state before deserializing, so nothing repopulates it. Consequence: any restart (scheduled, crash, deploy) while a siege is active permanently deletes all progress with no compensation, **and** the physical flag/beacon blocks placed in the world are never cleaned up (that only happens via the normal cancel/finish paths, neither of which runs for orphaned attacks) — they become permanent, un-completable ghost structures a human has to manually mine out. The test suite's own war fixture (`war.json` = `{"attacks":[]}`) never exercises a non-empty case, which is presumably how this regressed unnoticed. At a 200-player scale with routine restarts, this is likely the single highest-impact bug in the whole system.

**C3. The hidden-ore anti-dupe cache is in-memory-only and hard-capped at 2000 entries — trivially defeatable, no restart required.**
`Nodes.hiddenOreInvalidBlocks = OreBlockCache(2000)` is an LRU with **no serialization path anywhere** (confirmed via repo-wide grep). Two independent bypasses: (1) any server restart wipes it completely, making every previously-mined position farmable again; (2) even without a restart, the hard 2000-entry cap means a modest group of active miners can exhaust it in well under a minute at 200-player scale — once it wraps, the **oldest invalidated positions silently become mineable again**, so a coordinated group can cycle through >2000 positions to evict early entries, then loop back to the start for unlimited hidden-ore income. This is the exact "place block, break it, repeat" exploit the cache exists to prevent, reopened by its own size bound — a realistic, repeatable, economy-breaking dupe vector at this project's target scale, not a hypothetical.

### HIGH

**H1. A non-local `return` inside `Nodes.loadTerritories`'s `forEach` silently truncates territory loading.** `forEach` is inline in Kotlin, so a bare `return` (rather than `return@forEach`) inside its lambda exits the *entire enclosing function*, not just the current iteration — every other loop in the deserializer correctly uses labeled returns, strongly suggesting this is an oversight. A single malformed territory (core chunk missing from its own chunk list — an easy map-editor mistake) silently aborts loading of every other territory not yet processed in that batch. Reachable on both full world load and the partial hot-reload path, meaning a single bad live territory edit could partially corrupt a running server's territory index.

**H2. `Nation.load` throws an uncaught exception on bad save data, and `loadWorld()` has no catch — a single corrupted nation can silently drop all subsequent nations, skip all diplomacy setup, and then get permanently persisted over good data.** A missing/renamed capital town, or a nation with an empty towns list, throws directly (not a `Result`/nullable return like `Town.load` correctly uses). `Nodes.loadWorld()` has no `catch`, only `finally` — the exception propagates up to `Nodes.initialize()`, which just logs it and **continues startup** with whatever loaded before the crash point. Since nations are processed after towns and diplomacy setup runs after the nations loop completes, one bad nation entry means every nation after it never loads and **all alliance/enemy relationships across every nation silently vanish** — no crash, no player-visible error, just a server quietly running with broken diplomacy. Worse: the very next autosave writes this partial state back to `towns.json`, permanently destroying the un-loaded data.

**H3. Systemic mismatch between Minestom's per-chunk-parallel event dispatch and this codebase's plain (non-concurrent) collections.** This is a direct Bukkit-to-Minestom port, and Bukkit guarantees single-threaded plugin execution — this codebase was written under that assumption almost everywhere. Minestom's signature feature is parallel per-chunk/region ticking, meaning block events for different chunks can run concurrently by design. Confirmed unsynchronized, directly reachable from block-break/place/interact handlers: `Territory.town`/`.occupier` (plain `var`), `TerritoryChunk.attacker`/`.occupier` (plain `var`), `Town.protectedBlocks`/`.income.storage`, `OreBlockCache` (see C3), and `FlagWar.attackers`/`blockToAttacker` (plain `HashMap`, while `chunkToAttacker`/`occupiedChunks` in the *same class* were correctly converted to `ConcurrentHashMap` — a tell that this was a partial, incomplete fix, not an oversight born of not knowing the risk existed). Whether commands themselves run off the main thread is unconfirmed and should be checked directly against the Minestom version in use; the block-event path is well-documented Minestom behavior to be chunk-parallelizable regardless. At 200+ concurrent players spread across many chunks simultaneously mining/building/warring, this is a live risk, not a theoretical one — recommend either confirming Minestom funnels these specific event types through a single dispatch queue, or doing a real concurrency pass (concurrent collections, or funneling mutations through the main thread).

**H4. No player-facing town leadership transfer exists at all — an inactive or banned leader permanently soft-locks their town.** The only leadership-change path is `/nodesadmin town leader`, admin-only. Compounding this: the leader is **explicitly blocked from leaving** their own town ("you must transfer leadership before leaving"), and only the leader (not officers) can promote/demote. If a leader goes permanently inactive, quits, or is banned, no officer can promote anyone, no one can be demoted, and the town can never get new leadership without staff manually intervening — a routine, entirely avoidable support burden at 200+ players.

**H5. `Town.addResident` has no guard against a resident already belonging to another town, and none of the three call sites that add a resident re-check at the moment of acceptance.** `TownApplyCommand` doesn't check for a pending application/invite elsewhere; `TownAcceptCommand` doesn't re-verify `applicant.town == null` before accepting; `NodesAdminTownAddPlayerCommand` has the same gap. A player can apply to multiple towns simultaneously, or be accepted into town B after already being accepted into town A in the interim — the result is a resident whose `resident.town` field points at one town while still sitting, unremoved, in the *other* town's `residents` set: simultaneously counted as a member of two towns for population counts, chest trust, and income access, correctly reflected in only one.

**H6. Disconnecting while attacking kills the siege instantly, and the cancellation loop has a real crash/skip bug once more than one concurrent attack per player is allowed.** `onPlayerQuit` iterates a player's live `Attack` list calling `.cancel()` on each, which removes the just-cancelled element from the very list being iterated — a classic `ArrayList` mutate-during-iterate bug. At the default `maxPlayerChunkAttacks = 1` this is masked by coincidence; at 2 concurrent attacks the second is silently never cancelled; at 3+ it throws `ConcurrentModificationException` inside the disconnect handler, aborting cleanup of the rest. Independent of that specific bug, tying an entire multi-minute siege's fate to one player's live connection — with zero grace period — means ordinary network flakiness will routinely erase siege progress at 200-player scale, and turns "disconnect the enemy" (a known grief vector via lag/packet floods) into a reliable, silent counter to any attack that doesn't require ever finding the flag in the world.

**H7. Town/territory lifecycle operations never coordinate with active war state — deleting a town mid-siege can leave a territory simultaneously "unclaimed" and "occupied," permanently unresolvable through normal play.** None of `Town.destroy()`/`unclaim()`/`addTerritory()` touch `FlagWar`'s attack maps or `TerritoryChunk.attacker`/`.occupier`. If the *defending* town is deleted mid-siege, the attack still completes later against a now-null `territory.town`, falls through to an occupier-assignment branch that sets `.occupier` without ever setting `.town` — a state most other logic (including the enemy-check that gates all future attacks against it) doesn't anticipate, soft-locking the territory in limbo. If the *attacking* town is deleted instead, the completed attack assigns the captured territory to a Kotlin object reference for a town that no longer exists in `Nodes.towns` — an orphaned territory unmanageable via any player command.

**H8. `Resident.renderMinimaps()` is an unconditional, un-batched full broadcast to every online player, called from a wide range of individual war/diplomacy events — a real render-storm risk during large sieges.** Every single flag-attack lifecycle event (not just territory-level outcomes — every chunk capture) force-refreshes **every online player's minimap**, regardless of relevance or distance, with no coalescing/debounce. In a large coordinated push where dozens of chunks flip in a short window (realistic at 200-player scale, especially combined with the lack of any per-territory attack cap — see M-series below), each chunk capture queues up to 200 fresh async render computations onto the shared default thread pool — the same pool the war-state autosave writer uses with no exception handling (see M-series), meaning this contention risk and the silent-save-failure risk compound each other under exactly the load conditions a real siege would create.

### MEDIUM

- **M1** — `TownIncomeCommand`'s permission check reimplements a bespoke, incomplete copy of the five-group permission logic (`TOWN`/`TRUSTED` only, both additionally requiring in-town membership) instead of reusing `NodesWorldListener`'s correct evaluator — a leader who configures `income` access for `nation`/`ally`/`outsider` gets a false sense of working configuration; `/town income` silently continues denying everyone outside leader/officer/trusted-member no matter what's configured.
- **M2** — `Town.destroy()` doesn't invalidate outstanding invites pointing at it; an invitee who accepts after the town was deleted gets silently attached to an orphaned "zombie" `Town` object still alive only via a stale reference.
- **M3** — `TownProtectShowCommand` stacks unlimited concurrent particle-broadcast tasks with no dedup/cooldown, and `protectedBlocks` has no size cap — spamming the command creates N independent repeating tasks, each iterating the entire protected-blocks set every second for ~10 seconds; the clearest "no cooldown → load/self-grief vector" finding in the command surface.
- **M4** — Territory unclaim/capture never purges the losing town's plots — "ghost plots" persist in `town.plots` forever, unenforced day-to-day but silently reactivated (including old per-player permission grants for possibly-since-kicked members) the moment the same town later reclaims the same territory.
- **M5** — Kicking a resident clears their in-progress plot corner selection but never purges their per-player plot permission grants (`Plot.playerPermissions`, keyed by UUID) — silently reapplies without staff review if they rejoin later.
- **M6** — Manually-entered waypoint coordinates (via the creation dialog) are never validated against world bounds — a player can create a waypoint at Y ~999,999,999 or similarly nonsensical coordinates, in sharp contrast to the plot system (bounded by construction, since corners always come from real block-interaction events).
- **M7** — Several admin batch commands (`NodesAdminTownAddTerritoryCommand`/`RemoveTerritoryCommand`/`AddOfficerCommand`/`RemoveOfficerCommand`) discard the `Result`/`Boolean` outcome of each per-item operation and unconditionally report full success — an admin can be told "added 3 territories" when one silently no-oped (e.g. already owned, or was the town's protected home territory), specifically during the high-pressure moments (contested wartime territory changes) when accurate feedback matters most.
- **M8** — Town/Nation color-setting admin commands accept unbounded integer RGB values with no `.between(0, 255)` range check (unlike other numeric arguments in the same file, e.g. tier, which is correctly bounded) — persisted verbatim, unknown downstream behavior in minimap/map rendering.
- **M9** — The silk-touch check in hidden-ore handling (`inMainHand?.get(...)?.level(SILK_TOUCH) != 0`) treats a null/missing enchantment component the same as "silk touch present" due to the safe-call chain — plausible false-negative (ore disabled) for ordinary unenchanted tools, depending on Minestom's default component semantics; worth an explicit test.
- **M10** — `PlayerBlockInteractEvent` (doors/levers/redstone) skips wilderness permission checks entirely, unlike break/place — an explicit in-source comment suggests this is intentional, but it means interactive blocks in unclaimed wilderness can never be protected regardless of server config, an undocumented asymmetry with the rest of the permission model.
- **M11** — War-permission and occupier-permission bypasses can grant chest access that skips the "trusted only" lock even for the *owning* town's own untrusted members — plausible as intended wartime-looting design, but worth an explicit confirmation rather than assuming.
- **M12** — Home-teleport warmup only cancels on a full block-coordinate change, not any movement — sub-block strafing, small knockback, or edge-standing doesn't reset a pending teleport, weakening the anti-combat-log guarantee in exactly the PvP context this matters most for.
- **M13** — No FlagWar/occupation awareness in the friendly-fire damage listener — it only checks static nation/alliance relationships, so two players legitimately fighting over an active siege (attacker vs. defender) can be unable to damage each other in melee if they happen to share a nation/alliance, since the chunk-level "enemy" semantics FlagWar uses and the nation-level "enemy" semantics the damage listener uses are computed independently and can disagree.
- **M14** — Sneaking activates a 3x wider minimap render radius (~9,000+ chunk-cell lookups vs. ~3,800 standing), off the main thread but still real CPU on a shared, unmanaged thread pool — a battle where many combatants sneak simultaneously (a common PvP posture) compounds directly with the render-storm risk in H8.
- **M15** — Minimap rendering and war-state autosaving share the same unmanaged default thread pool (`ForkJoinPool.commonPool()`), and the war-save path has **no exception handling at all** — a thrown exception during a busy siege silently drops that save cycle with no log trace.
- **M16** — `WarSerializer`'s pre-processing buffers are shared mutable singleton state, cleared and rebuilt by each `save()` call while a previous async write may still be iterating them — a genuine mutate-while-iterate race under I/O contention during a busy war, compounding H2/M15.
- **M17** — No overlap validation between territories at world-load time — nothing stops two territories from claiming the same chunk in `world.json`; the later one silently wins with no error logged.
- **M18** — Hardcoded legacy 0–255 world-height assumption in `OreSampler` and `Territory.defaultSpawnLocation` — if this server ever runs Minestom instances with modern extended world height, ore sampling and default spawn placement both silently misbehave outside that range.
- **M19** — `Town.TownSaveState.permissions` breaks its own documented "immutable snapshot" contract — the array is cloned but each slot still shares a live, mutable `EnumSet` reference with the running `Town`. A permissions-changing command running while the async save serializer is mid-iteration over the same `EnumSet` is a genuine concurrent read-during-mutation on a non-thread-safe collection — worst case, a silently-swallowed exception in the untracked `CompletableFuture.runAsync` save task means `towns.json` simply doesn't get written that cycle with no error surfaced anywhere.
- **M20** — Silent, unlogged data loss for unrecognized `Material` keys when deserializing a town's stored income — every other parse failure branch in the same file logs to stderr; this one doesn't, so a version bump or hand-edit typo can vanish real player-earned currency with zero trace.

### LOW

- Non-atomic `townNametagIdCounter++` increment — concurrent `Town` construction could produce duplicate scoreboard-team nametag IDs, causing wrong ally/enemy color display.
- `Town.destroy()` doesn't clean up `plots`/`protectedBlocks`/pending `applications` (the applications' 60s expiry task still fires later against an orphaned map — harmless but a small resource leak).
- `Town.setHome` silently overwrites any custom `/town setspawn` with no warning whenever the home territory changes.
- `Nation.removeTown`'s new-capital selection after the old capital leaves is `HashSet.first()` — deterministic per UUID but essentially arbitrary from a game-design perspective, with no seniority/vote mechanism.
- `Resident.fromName`/waypoint-visibility cleanup do full linear scans over all residents — an O(n) cost on routine command paths that will add up over a server's lifetime.
- `Plot.validate` doesn't clamp Y-bounds against actual instance world height, only against the configured max plot dimensions.
- `IncomeInventory`'s own in-source comment acknowledges an unresolved item-dupe race between clearing the visual inventory and persisting to disk on a crash — a known, documented, still-open vector.
- Dead/vestigial code: per-town `allies`/`enemies` are parsed from JSON but never written (alliances are nation-scoped only) — harmless today, but could mislead a future maintainer into thinking town-level overrides are supported.
- `/nation help`'s text lists a `/nation color` command that doesn't exist as a player command (it's admin-only) — and disagrees with the top-level `/nation` help text about what commands exist at all.
- `ArgumentTerritory` (singular) uses an unguarded `.toInt()` instead of `.toIntOrNull()` (unlike its array-argument sibling, which got this right) — a bad `/territory <id>` argument throws a raw `NumberFormatException` instead of the intended graceful syntax error.
- The player's own Minecraft username is the one persisted name that never goes through the `ArgumentSanitizedString` defense (because it isn't a command argument) — safe under normal Mojang online-mode auth, but a real gap if this server or a proxy in front of it ever runs offline-mode.
- Sky beacon (the tall, far-visible siege marker) silently fails to render for any legal flag placed roughly Y 206–252 due to an off-by-one in the beacon-height range calculation — a very plausible altitude for mountain fortresses, with no error or log.
- No per-territory/per-defender cap on simultaneous attacks — a numerically larger side can trivially field dozens of simultaneous attackers against one territory's border chunks, more a balance question than a bug given the 200-player target.
- Sub-block movement doesn't cancel a pending teleport warmup on plugin-driven teleports (`EntityTeleportEvent`) at all, only on client movement — a minor double-teleport consistency risk.
- No cooldown on territory-crossing chat announcements — rubber-banding or edge-riding across a chunk border can spam repeated enter/leave messages to oneself.
- `OreSampler`'s Y-range fill loop has a genuine off-by-one that can leave the single topmost configured Y-level unsampled (never yields ore) depending on how ore ranges are configured relative to the world-height ceiling.
- No cap on simultaneous outstanding town applications — a player can spam `/t apply` against every town on the server with no per-player/per-town throttle, messaging every town's leadership each time.
- `TownInviteCommand`'s self-invite error message is copy-pasted from an unrelated scenario and is misleading.
- A handful of now-unreachable null checks in command code (`ArgumentResident`/`ArgumentTown`/etc. can never actually resolve to null given how they're implemented) — harmless, but a sign of copy-paste from an older resolution model, worth cleaning up so it isn't misread as meaningful defensive logic later.
- `WarSerializer` keys occupied-chunk records by town *name* (a string) — if towns can be renamed, an occupied-chunk record could silently fail to resolve back to its town on the next load, reverting the territory to unoccupied with no liberation message.
- Hardcoded exhaustive `when` blocks on the two current minimap zoom scales (4/12) will throw if a third scale is ever added without updating every site — a maintenance trap, not a current bug.

## Part 4 — Divergences from the original (phonon) design

- **The original's power-point claiming economy does not appear to exist in the Aechronis port.** Nothing in the reviewed source implements a power budget, claim cost formula, or unclaim penalty — territory assignment in `nodes` (Aechronis) appears to happen purely through `NodesAdminTownCreateCommand`/`addTerritory`/FlagWar capture, not a player-driven power-based claiming system. Worth explicitly confirming this is an intentional design change (e.g., admin-curated territory assignment replacing organic claiming, consistent with RESEARCH.md §9's "curated roster" decision) rather than a gap.
- **Peace treaties/truces (48-hour default) from the original docs were not confirmed present** in the reviewed war code — the audit passes focused on FlagWar's attack/capture mechanics and didn't find an equivalent `/peace` truce system, but this wasn't exhaustively ruled out either. Worth a direct follow-up check if peace mechanics matter to the design.
- **The territory-tier system** (income/mining bonuses, 1–10, staff-assigned) is documented in `Aechronis/guides` but genuinely unimplemented in `nodes` itself — already covered in depth in RESEARCH.md §15, cross-referenced here since it's directly relevant to this document's territory/attribute findings (the `attackerTimeMultiplier`/`defenderTimeMultiplier` hook point noted in §2.1/§2.3 above is exactly where a tier-driven capture-time bonus would plug in).

## Part 5 — Priority order if hardening this before launch

1. **C2 (war persistence)** and **H2 (uncaught Nation.load exception)** — both are silent, unbounded data-loss bugs that get worse the longer the server runs undetected; fix before any real playtesting with persistent state you care about.
2. **C3 (ore anti-dupe cache)** — directly undermines the mining/economy design this whole project is built around (RESEARCH.md §11); fix before opening any economy-facing playtest.
3. **C1 (port-naming bug)** — trivial fix (use `context[nameArg]`), but blocks the `Port`/building system entirely past the first use.
4. **H3 (thread-safety mismatch)** — needs a definitive answer (confirm Minestom's actual threading guarantees for the event types in question) before scaling past small-scale testing, since it underlies several other findings (M-series ore/war-state races).
5. **H4/H5 (leader lock-out, double-town-membership)** — both are routine, foreseeable support burdens at real player counts; fix before any real community relies on the town system.
6. **H6/H7 (war-state coordination with disconnects and admin actions)** — fix before running any real siege/war content live, since both are easy to trigger by accident (a normal disconnect, a normal admin town-deletion) not just adversarially.
7. **H8 + M14/M15/M16 (minimap/save render-storm cluster)** — these compound each other specifically under "a big war is happening," which is exactly when you most need the server not to fall over; worth load-testing this cluster specifically once the flagship shard load-testing (RESEARCH.md §7) happens.
8. Everything else in MEDIUM/LOW — real, but lower urgency; good backlog for ongoing hardening rather than launch blockers.
