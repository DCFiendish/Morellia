Practical effect: `morellia-server` (this project's own scaffold, now live at `server/`) still needed to be built from scratch either way — that part of the original conclusion holds — but "the public repos are the whole picture" doesn't, so don't assume something's absent from Aechronis's real setup just because it's absent from the public libraries.
- ~~RESOLVED (2026-07-30): no private Aechronis "server" repo exists.~~ Superseded by the correction above — kept struck through rather than deleted so the reasoning trail (and why it was wrong) stays visible.
- **RESOLVED (2026-07-30): Minestom test-harness gap is smaller than assumed.** `utils` (current `master`) now ships `src/main/kotlin/net/aechronis/utils/TestServer.kt` — a real, working `createTestServer()` helper that spins up a live `MinecraftServer` instance with a flat test world, configurable spawn/gamemode, and a built-in MSPT/memory boss bar for manual playtesting. This isn't a `MockBukkit`-style unit-test mock, but it is exactly the "integration-style test against a real Minestom instance" building block described below — don't build one from scratch, use this.
- Still needed: decide what's actually worth testing on top of this foundation:
  - Pure-logic unit tests for things like the ore-sampler math, income calculations, FlagWar attack-time formulas — these don't need a running server and are cheap to add, `TestServer.kt` isn't needed for these.
  - Integration-style tests built on `createTestServer()` — higher value for catching the concurrency/threading bugs flagged in `01-concurrency-model.md` (e.g. the command-threading question that doc leaves open could actually be settled with a test built on this harness), but higher setup cost.
  - Decide a minimum bar (e.g. "new economy/combat-tag/anti-cheat code gets unit tests, bug fixes to existing library code don't require retrofitting tests") rather than an all-or-nothing policy.
  - Check whether `combat`/`nodes`/`vanilla` themselves already have `*Test.kt` files using `TestServer.kt` or a predecessor pattern (their `build.gradle.kts` all declare `testImplementation("org.jetbrains.kotlin:kotlin-test")`/JUnit) — `CombatTest.kt`, `NodesTest.kt`, and `VanillaTest.kt` all exist per the git history pulled during this session and were recently expanded (e.g. combat's test file grew by 300+ lines in the commits pulled this session) — read these before designing `world-server`'s own test approach, they're a working precedent, not a blank slate.
- Load-testing methodology itself is covered in `05-hosting-and-ops.md` — don't duplicate here, but note the dependency: QA process and load-testing plan should probably be designed together since they'll likely share tooling (e.g. a bot-simulation harness useful for both functional and load testing, and `TestServer.kt` is a plausible foundation for that too).

## Legal/business-adjacent (lighter pass — not a full legal review)

- **Mojang commercial-usage/EULA compliance** — only relevant if any monetization (a premium/cosmetic currency, per `06-economy-and-progression.md`'s deferred currency decision) ever ships. Currently fully deferred project-side, but worth a light read of Mojang's current commercial usage guidelines now so it's not a surprise later if/when a currency decision is made. Key constraint to confirm: cosmetic-only monetization, no pay-to-win mechanics — check this against whatever the eventual currency/voucher design (§06) actually grants.
- **Basic data-handling posture** — not a full GDPR audit, but a sanity check: `PlayerData` (vanilla), `nodes`' JSON saves, and `logger`'s H2 database all persist player-identifying information (UUIDs, usernames, sometimes IP via join logging). Worth a basic pass on what's actually stored, for how long, and whether a player-data-deletion request could realistically be honored if one ever came in — this is a much smaller lift now (documenting current state) than retrofitting deletion support later.
- **Corrected (2026-07-30): `aechronis.net` is NOT this project's domain.** Confirmed directly with the user: Aechronis is a separate, third-party Minestom server whose `nodes`/`combat`/`vanilla`/`utils` code is being adopted as technical infrastructure — this project is a different server with its own (not-yet-decided) name. The `play.aechronis.net`/`map.aechronis.net`/`bans.aechronis.net`/`store.aechronis.net`/`discord.aechronis.net` infrastructure found in `Aechronis/guides` belongs to Aechronis's own real, apparently-previously-live community (casual in-community tone, existing bans/store/Discord) — interesting context for understanding the code's origin, but **not this project's domain, Discord, or community to configure.** This means the domain/DNS decision for this project is still fully open: a domain hasn't been chosen because **the project itself doesn't have a name yet** — that's the actual first open item here, upstream of DNS.
- `07-community-and-onboarding.md`'s "Discord structure not yet designed," server access/whitelist model, and staff tooling are correctly scoped as this project's own from-scratch decisions — Aechronis's existing Discord/bans-site don't answer any of them, they're a different community's infrastructure.
